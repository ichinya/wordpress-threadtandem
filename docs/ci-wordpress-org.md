# Публикация в WordPress.org из GitHub

Workflow `.github/workflows/wordpress-org.yml` проверяет плагин и собирает ZIP штатным `tools/build.ps1`. Публикация запускается только при push; pull request проходит проверки без доступа к SVN-паролю.

| Событие | Результат в SVN |
| --- | --- |
| Push в `main` | Пакет последнего коммита этого push заменяет содержимое `trunk/`. `Stable tag` сохраняет последний опубликованный релиз. |
| Push Git-тега `vX.Y.Z` или `X.Y.Z` | Пакет **коммита тега** создаётся в `tags/X.Y.Z`. Указатель `Stable tag` в trunk обновляется этим же SVN-коммитом, если версия новее текущего релиза. |
| Pull request в `main` | Проверки и ZIP-артефакт; без публикации. |

Номер версии автоматически не меняется. Перед будущим выпуском владелец сам меняет PHP-заголовок `Version`, константу `TREDA_VERSION` и `Stable tag` в исходном `readme.txt`, а затем создаёт тег. Все три значения должны совпасть с номером тега. Поддерживаются только финальные версии `X.Y.Z`; префикс `v` используется только в Git.

## Однократная настройка

В [настройках Actions secrets репозитория](https://github.com/ichinya/wordpress-threadtandem/settings/secrets/actions) добавьте repository secret **`WPORG_SVN_PASSWORD`** — отдельный SVN-пароль WordPress.org пользователя **`Ichi-nya`**. Пароль профиля WordPress.org не подходит. Получить SVN-пароль можно в [Account & Security](https://profiles.wordpress.org/me/profile/edit/group/3/?screen=svn-password).

После добавления секрета и слияния workflow в `main` очередной push обновит trunk. Теги, существовавшие до появления workflow, автоматически не публикуются. Фактическую публикацию проверяйте по шагу `Publish main to trunk or version tag to SVN tags` во вкладке Actions. ZIP в артефактах сам по себе не подтверждает публикацию.

## Поведение и ограничения

- SVN: `https://plugins.svn.wordpress.org/threadtandem-sync-for-telegram/`. Пользователь `Ichi-nya` задан в инструменте; пароль поступает через stdin, не аргументы процесса, и не сохраняется в SVN auth cache.
- В trunk при разработке остаётся версия последнего релиза в поле `Stable tag`. Например: исходный код уже `1.2.0`, опубликован `1.1.0` — пользователи продолжают получать `tags/1.1.0`. При выпуске `v1.2.0` создаётся `tags/1.2.0`, и указатель переключается на него.
- Тег берёт файлы точно из своего Git-коммита. Более новый код trunk сохраняется, даже если релизный тег поставлен на более ранний коммит. Только `Stable tag` переключается вперёд.
- Старые SVN-теги не перезаписываются. Повторный запуск с теми же файлами ничего не меняет; другие файлы под существующим номером вызывают ошибку. Выпуск старого номера не понижает текущий `Stable tag`.
- Публикации выполняются последовательно; GitHub ставит до 100 ожидающих заданий в очередь ([`queue: max`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idconcurrency)). Технический порядок запуска GitHub не гарантирует. SVN-свойство `threadtandem:git-commit` и проверка Git-истории предотвращают откат trunk запоздавшим заданием main. Не используйте force-push для main: при разветвлении истории инструмент останавливается для ручной сверки.
- Изменения `trunk` и новый SVN-тег коммитятся атомарно. Ошибка до коммита не публикует половину релиза. После сетевой ошибки результат проверяется повторным запуском: существующий идентичный тег безопасно пропускается.
- У SVN уже должны существовать `trunk/` и `tags/`. Для пустого репозитория сначала нужен релизный Git-тег. Для текущего плагина начальный релиз `1.1.0` уже опубликован.
- SVN `/assets` с иконкой, баннерами и скриншотами этот workflow не меняет. Папка `assets/` **внутри пакета** содержит рабочие JS/CSS плагина и публикуется вместе с кодом.
- `.info`, локальные настройки, документация, тесты, инструменты и GitHub workflow в пакет не входят. Дополнительная проверка allowlist и похожих на bot token строк выполняется перед обращением к SVN.
- Workflow выполняет PHP/JS syntax checks, автономные PHP-тесты и тесты публикации на временном локальном SVN. Интеграционные тесты WordPress, Plugin Check и проверка на сайте остаются отдельными проверками перед выпуском.

Для проверки инструмента локально нужны Python 3.10+, Git, `svn` и `svnadmin`:

```sh
python3 -m unittest discover -s tests -p 'test_svn_deploy.py' -v
```

Тесты используют вымышленный пакет версии `9.8.7` и `file://` SVN; к WordPress.org и Telegram не подключаются. Если SVN не в PATH, задайте `SVN_BINARY` и `SVNADMIN_BINARY` абсолютными путями к исполняемым файлам.

WordPress.org [рекомендует использовать SVN для готовых релизов](https://developer.wordpress.org/plugins/wordpress-org/how-to-use-subversion/). Здесь выбран запрошенный владельцем режим main → trunk, а выпуск для пользователей контролируется отдельным Git-тегом и указателем `Stable tag`.
